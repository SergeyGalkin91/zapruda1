### Отдельное одобрение зоны общения

- `record_spot` сохраняет условие проверенного одобренного SPOT. `community` использует существующую комнату `spot-zone` и отдельную приватную запись одобрения. Для `community` FK на рекордный SPOT пуст. Тип и область зоны фиксируются при создании.
- Оператор БД вызывает приватную `review_community_zone(uuid,boolean,text)` со служебным идентификатором решения владельца. Запись одобрения хранит время, роль БД и привязку к комнате. У `anon`, `authenticated` и `service_role` нет доступа к журналу и функции одобрения. Обычная установка `approved=true` требует действующего одобрения.
- Каталог, вступление, RLS чата и социальные операции используют общий критерий доступности. Каталог и вступление требуют активную подтверждённую сессию. Вступление остаётся добровольным. Каталог возвращает прежние шесть полей с грубой областью.
- Отзыв одобрения закрывает чтение и новые операции после фиксации транзакции. Прежняя логика закрытия отзывает присутствие, ожидающие приглашения, оповещения и доступ к совместным фото. Отзыв окончательный для этой записи зоны. Повтор с тем же идентификатором решения идемпотентен. Rollback закрывает зоны общения, сохраняя аудит и рекордные зоны.
- Дополнение требует обеих предыдущих дельт и отказывается запускаться без механизма отзыва. SQL проверен в изолированном PostgreSQL и хранится как `DRAFT_` до формирования версионной STAGING-миграции через CLI. Доступного локального рантайма для CLI в этом срезе не было. Изменены SQL и тесты, актуальный Premium UI сохранён.
